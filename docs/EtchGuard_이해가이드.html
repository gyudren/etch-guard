EtchGuard는 식각 장비의 최근 10시간(20사이클) 센서로 30분 뒤 이상 점수를 예측합니다. 이 페이지는 그 과정을 그림으로 따라갑니다. 맨 위 지도에서 흐름 버튼을 누르면 해당 경로만 강조되고, 아래 절에서는 각 단계를 실제 측정값으로 확대해서 봅니다.

전체 지도데이터와 시간 분할요청 하나의 여정Lazy vs Eager버전과 게이트드리프트 판정재학습 시퀀스게이트 재검증Docker코드 지도

00전체 지도

세 개의 띠로 나뉩니다. 위는 오프라인에서 모델을 만들고 배포 여부를 정하는 MLOps※2, 가운데는 컨테이너 안에서 요청을 받는 서빙※1, 아래는 예측 오차※4를 지켜보다가 스스로 재학습하는 AIOps※3입니다. 아래 띠의 결과가 다시 위(Registry)와 가운데(ModelManager)로 돌아가면서 루프가 닫힙니다.

전체 루프

업로드 → 학습 → 게이트 → Production → 서빙 → 예측 기록 → 드리프트 판정 → 알림 → 재학습 → 재검증 → 재배포까지 끊기지 않고 이어집니다.

  1. 학습 결과는 게이트를 통과해야만 Registry의 Production이 됩니다.
  2. 서빙은 항상 Production을 읽습니다(Docker는 Eager).
  3. 확정 점수가 들어오면 예측 오차로 모델 상태를 판정합니다.
  4. 드리프트면 재학습하고, 다시 게이트를 통과해야만 교체합니다.
※ 개념 짚기
※1
모델 서빙

학습된 모델을 API로 감싸 다른 시스템이 호출할 수 있게 하는 것입니다. 노트북 안의 모델은 현장에서 쓸 수 없습니다.

FastAPI POST /predict가 모델의 입구입니다.

※2
MLOps

모델을 기록하고, 버전으로 관리하고, 검증된 것만 배포하는 체계입니다. 모델을 믿고 바꿀 수 있게 합니다.

MLflow 기록·Registry·배포 게이트·Docker가 여기에 해당합니다.

※3
AIOps

배포된 모델을 계속 지켜보다가 성능이 떨어지면 알리고 스스로 재학습·재배포하는 운영 자동화입니다.

드리프트 판정 → [WARN] → 재학습 → 재검증 → 교체.

※4
예측 오차와 확정 점수

공정이 끝난 뒤 계측으로 확정되는 실제 이상 점수(라벨)와 예측의 차이입니다. 코드 에러가 없어도 모델이 틀리는지 알려 주는 유일한 신호입니다.

/predict/batch-test로 확정 점수가 들어와 (예측, 실제) 쌍이 됩니다.

01데이터와 시간 분할

장비 5대의 3년치 기록을 시간 순서대로 자릅니다. 무작위로 섞지 않는 이유는 미래 데이터로 과거를 맞히는 누설※5을 막기 위해서입니다. 스케일러※6와 계절 기준 분포※7는 학습 구간(2023–2024)에서 한 번만 만들고 이후 계속 재사용합니다.

※ 개념 짚기
※5
시간 기반 분할과 데이터 누설

시계열은 섞지 않고 시간 순으로 자릅니다. 미래 정보가 학습이나 입력에 섞이면 성능이 실제보다 좋아 보입니다.

2023–24 학습 / 2025 검증·테스트 / 07-20 이후 드리프트. 입력에 정답 필드가 오면 422.

※6
스케일러와 학습-서빙 일치

센서마다 단위가 달라 0~1로 맞추는 min-max 정규화입니다. 학습과 서빙의 기준이 다르면 같은 값이 다른 숫자로 들어갑니다.

scaler.json을 학습 구간에서 한 번만 fit하고 모델과 한 번들로 묶어 계속 씁니다.

※7
계절성과 같은 달 기준

매년 반복되는 정상 변화입니다. 전월과 비교하면 여름을 드리프트로 오인합니다.

외기·습도·냉각수 PSI가 같은 달 기준이면 0.28~0.46, 연간 통합 기준이면 4.7~5.6입니다.

02요청 하나의 여정

식각 장비※8의 최근 20사이클※10로 30분 뒤 이상 점수※9를 묻는 /predict 호출 하나를 따라갑니다. 입력 검증※11과 전처리가 모델 앞에 있고, 학습 때 쓴 것과 같은 transform()과 같은 scaler.json을 씁니다.

※ 개념 짚기
※8
식각(Etch)과 FDC

플라즈마로 웨이퍼 막을 패턴대로 깎는 공정입니다. FDC는 센서마다 고정 상·하한을 두는 기존 감시 체계입니다.

센서 하나가 아니라 12종을 20사이클 동안 함께 보고 점수 하나로 요약합니다.

※9
이상 점수와 위험 등급

장비 상태를 0~100으로 나타낸 값입니다. 70 이상 HIGH, 40~70 WARNING, 40 미만 NORMAL입니다.

지금이 아니라 30분 뒤 공정의 점수를 예측합니다.

※10
사이클과 SEQ_LEN

사이클은 장비 한 번의 공정(30분), SEQ_LEN은 모델이 한 번에 보는 과거 사이클 수입니다.

SEQ_LEN = 20(10시간). 입력 모양은 (20, 12)입니다.

※11
입력 스키마와 422

요청 형식을 Pydantic으로 정의하고, 어긋나면 모델을 부르기 전에 422로 거부합니다.

20개 정확히, 30분 간격 시간순, 압력·RF 양수, 정의되지 않은 필드 금지.

03Lazy vs Eager: 기다림을 언제 치르는가

모델을 메모리에 올리는 데 약 2.5초가 걸립니다. Lazy는 그 시간을 첫 사용자가, Eager는 서버 기동이 치릅니다※12. 아래 막대는 실제 측정값을 같은 시간 축에 그린 것입니다.

※ 개념 짚기
※12
Lazy / Eager 로딩

모델을 첫 요청 때 올리느냐(Lazy), 서버가 뜰 때 올리느냐(Eager)입니다. 누가 로딩 시간을 기다리느냐가 달라집니다.

Lazy 첫 요청 2.60초, Eager 첫 요청 0.031초. Docker는 Eager.

※13
/health와 /ready

/health는 프로세스가 살아 있는지, /ready는 모델을 들고 요청을 받을 준비가 됐는지를 봅니다.

Docker HEALTHCHECK가 /ready를 확인합니다. 모델이 없으면 503.

04버전과 배포 게이트

학습할 때마다 MLflow에 새 버전이 기록되지만※14, 서빙이 읽는 것은 @Production 별칭※15이 가리키는 한 버전뿐입니다. 게이트※16를 통과한 버전만 별칭을 가져갈 수 있고, 게이트는 RMSE※17와 HIGH 등급의 Precision·Recall※18로 판단합니다.

※ 개념 짚기
※14
실험 추적 (MLflow Tracking)

학습할 때마다 설정(params)·성능(metrics)·결과물(artifact)을 기록해 어떤 모델이 어떻게 만들어졌는지 남기는 것입니다.

데이터 해시, epoch, 검증·테스트·드리프트 지표를 실험 EtchGuard-AIOps에 남깁니다.

※15
레지스트리 · 버전 · alias

등록된 모델의 버전 목록이고, alias는 특정 버전을 가리키는 이름표입니다.

서빙은 models:/Semiconductor_Etch_LSTM@Production만 읽으므로 버전이 늘어도 코드는 그대로입니다.

※16
배포 게이트

정해진 품질 기준을 넘은 모델만 운영에 올리는 관문입니다. 실패해도 기록은 남습니다.

검증 RMSE ≤ 4.0, HIGH Recall ≥ 0.80, Precision ≥ 0.80.

※17
RMSE

예측과 실제의 차이를 제곱해 평균낸 뒤 제곱근을 씌운 값입니다. 큰 오차에 더 민감하고 단위가 점수와 같습니다.

√(mean((실제−예측)²)). 정상 테스트 3.08점, 드리프트 구간 8.07점.

※18
Precision과 Recall

Precision은 HIGH라고 울린 경보 중 진짜 비율(오경보의 반대), Recall은 진짜 HIGH 중 잡아낸 비율(미탐의 반대)입니다.

바로 위 혼동행렬 그림 참고. 미탐은 불량 웨이퍼로, 오경보는 불필요한 점검으로 이어집니다.

05드리프트 판정: 한 번 튄 것과 계속 나쁜 것

확정 점수가 들어오면 장비별로 (예측, 실제) 쌍을 24개(12시간)씩 묶어 RMSE를 계산합니다. 5.0을 넘는 윈도우※21가 3번 연속이면 드리프트※19입니다. 1회가 아니라 3회 연속인 이유는 오탐과 미탐※22의 균형 때문입니다. 판정은 예측 오차로 하고, 입력 분포(PSI※23)는 원인 센서를 짚는 데만 씁니다※20. 아래는 최종 실행의 실제 윈도우 값입니다.

※ 개념 짚기
※19
데이터 드리프트와 컨셉 드리프트

입력 분포가 바뀌는 것이 데이터 드리프트, 같은 입력에 대한 정답 관계가 바뀌는 것이 컨셉 드리프트입니다. 둘 다 에러 없이 예측을 틀리게 만듭니다.

07-20 이후 압력↑ RF↓ 진동↑와 열화 가속이 겹쳐 RMSE가 3.08 → 8.07.

※20
성능 모니터링 vs 입력 모니터링

정답이 있으면 예측 오차로 직접 판정하고, 정답이 늦으면 입력 분포 변화로 먼저 추정합니다.

판정은 오차(RMSE), 입력 분포(PSI)는 원인 센서 진단용입니다.

※21
윈도우와 연속 판정

오차를 일정 개수씩 묶어 판단하는 단위입니다. 짧으면 노이즈에 민감하고 길면 반응이 느립니다.

24쌍(12시간) 윈도우, 5.0 초과 3회 연속이면 DRIFT, 1~2회는 WATCH.

※22
오탐·미탐과 알람 피로

기준을 낮추면 미탐이 줄고 오탐이 늘며, 높이면 반대입니다. 오탐이 잦으면 사람들이 경보를 무시합니다.

1회 판정은 정상 중 장비당 월 2.06회 오탐, 3회 연속은 0회(탐지 36시간).

※23
PSI

기준 분포와 현재 분포를 구간별로 비교한 값입니다. Σ (현재−기준) × ln(현재 ÷ 기준), 관례상 0.25 이상이면 크게 변한 것으로 봅니다.

열화 때문에 정상에서도 1 이상이 흔해서, 평상시 대비 배율(×10.2 등)로 원인 센서 순위만 매깁니다.

06재학습 시퀀스: 3초 동안 일어나는 일

드리프트 배치를 보낸 요청은 재학습을 기다리지 않고 곧바로 200을 받습니다. 재학습은 백그라운드 스레드※24에서 돌고, 통과하면 서빙 모델을 멈추지 않고 갈아 끼웁니다※25. 시각은 최종 실행의 aiops.log 기준입니다.

※ 개념 짚기
※24
백그라운드 작업과 락

오래 걸리는 일을 요청 처리와 분리하고, 같은 일이 동시에 두 번 돌지 않게 막는 것입니다.

batch-test는 즉시 200을 받고, 재학습 중 다른 장비는 retrain_in_progress.

※25
무중단 교체 (hot swap)

서비스를 멈추지 않고 모델을 바꾸는 것입니다. 캐시를 비우기만 하면 다음 요청이 느려지고, 안 비우면 옛 모델이 계속 응답합니다.

reload()가 새 모델을 먼저 로드한 뒤 참조만 교체합니다.

07게이트 재검증: 무엇을 통과해야 교체되나

재학습 후보는 세 가지를 동시에 만족해야 합니다. 최근 홀드아웃에서 기본 게이트를 넘고, 현 Production보다 낫고※27, 드리프트에 맞추다가 정상 상태를 잊지 않았는지※26 고정 정상셋으로 확인합니다. 하나라도 못 넘으면 기존 버전이 그대로 서비스됩니다※28.

※ 개념 짚기
※26
Fine-tuning · warm start · 망각

이미 학습된 가중치에서 이어서 조금 더 학습하는 것입니다. 적은 데이터로 처음부터 학습하면 불안정하고 과거 패턴을 잊습니다(망각).

최근 7일로 lr 1e-4 × 10 epoch. 처음부터 학습하면 정상셋 RMSE 6.43.

※27
Champion / Challenger · 회귀 테스트

서비스 중인 모델과 후보를 같은 데이터로 비교하고, 예전에 잘 하던 것을 여전히 잘 하는지 고정 데이터로 다시 확인하는 것입니다.

홀드아웃 7.86 → 2.64, 고정 정상셋 2,410건 RMSE 3.39 ≤ 4.0.

※28
롤백

문제가 생겼을 때 이전 버전으로 되돌리는 것입니다. 게이트 실패 시 기존 버전 유지가 자동 롤백 역할을 합니다.

수동으로는 registry rollback --version N. 게이트 통과 이력이 있는 버전만 허용.

08Docker: 빌드할 때 끝내 두는 것과 실행할 때 하는 것

이미지※29를 만들 때 학습·등록·승격까지 끝내 두므로, 컨테이너는 뜨자마자 Production 모델을 들고 시작합니다. 호스트의 MLflow DB를 복사하지 않아서 절대경로 문제가 없고, 의존성은 소스보다 먼저 설치해 레이어 캐시※30를 활용합니다.

※ 개념 짚기
※29
이미지와 컨테이너

이미지는 코드·라이브러리·모델을 묶은 실행 꾸러미, 컨테이너는 그 이미지를 실제로 띄운 실행 단위입니다. 어디서나 같은 환경이 됩니다.

빌드 때 학습·등록을 끝내 두고, 실행하면 Eager로 바로 서빙합니다.

※30
레이어 캐시

Dockerfile의 각 줄이 층으로 저장되어, 바뀌지 않은 층은 다시 실행하지 않는 것입니다.

requirements를 먼저 설치하므로 코드만 바뀌면 TensorFlow 재설치가 생략됩니다.

09코드 지도

그림의 각 단계가 어느 파일의 어떤 함수인지, 실습 가이드의 TODO와 어떻게 대응하는지 정리했습니다.

단계파일 · 함수가이드 TODO하는 일
업로드·검증data.read_data · app.upload—필수 열, 30분 간격, 장비별 연속성, 값 범위 검증 후 저장
