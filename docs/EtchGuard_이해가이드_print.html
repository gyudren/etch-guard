1이 시스템이 푸는 문제

식각 장비는 완전히 멈추기 전에 센서가 먼저 조금씩 흔들립니다. 그런데 센서별 고정 경보는 자주 틀리고, 장비 5대 × 센서 12종 × 하루 48사이클이면 하루 측정값이 2,880개라 사람이 다 볼 수도 없습니다. 그 사이 이상 상태로 진행된 웨이퍼는 사후 계측에서야 불량으로 드러납니다.

개념 짚기
※1
모델 서빙

학습된 모델을 API로 감싸 다른 시스템이 호출할 수 있게 하는 일입니다. 노트북 안에만 있는 모델은 현장에서 쓸 수 없습니다.

FastAPI의 POST /predict가 모델의 입구입니다.

※2
MLOps

모델을 기록하고 버전으로 관리하며, 검증을 통과한 것만 배포하는 체계입니다. 모델을 믿고 바꿀 수 있게 해 줍니다.

MLflow 기록, Registry, 배포 게이트, Docker가 여기에 속합니다.

※3
AIOps

배포된 모델을 계속 지켜보다가 성능이 떨어지면 알리고, 스스로 재학습하고 다시 배포하는 운영 자동화입니다.

드리프트 판정 → [WARN] 알림 → 재학습 → 재검증 → 교체로 이어집니다.

※4
예측 오차와 확정 점수

확정 점수는 공정이 끝난 뒤 계측으로 정해지는 실제 이상 점수(라벨)입니다. 예측과 이 값의 차이는 코드 에러 없이 모델이 틀리고 있는지 알려 주는 유일한 신호입니다.

/predict/batch-test로 들어와 (예측, 실제) 쌍이 됩니다.

2전체 지도

시스템은 세 띠로 나뉩니다. 위는 오프라인에서 모델을 만들고 배포 여부를 정하는 곳, 가운데는 컨테이너 안에서 요청을 받는 서빙, 아래는 예측 오차를 지켜보다가 스스로 재학습하는 AIOps입니다. 아래 띠의 결과가 다시 위의 Registry와 가운데의 ModelManager로 돌아가면서 루프가 닫힙니다.

3데이터와 시간 분할

장비 5대의 3년 치 기록을 시간 순서대로 자릅니다. 무작위로 섞지 않는 이유는 미래 데이터로 과거를 맞히는 누설※5을 막기 위해서입니다. 스케일러※6와 월별 기준 분포※7는 학습 구간(2023–2024)에서 한 번만 만들고 이후 계속 재사용합니다.

개념 짚기
※5
시간 기반 분할과 데이터 누설

시계열은 섞지 않고 시간 순서대로 자릅니다. 미래 정보가 학습이나 입력에 섞이면 성능이 실제보다 좋아 보입니다.

2023–24 학습, 2025 검증·테스트, 07-20 이후 드리프트. 입력에 정답 필드가 들어오면 422로 거부합니다.

※6
스케일러와 학습-서빙 일치

센서마다 단위가 달라 값을 0~1로 맞추는 min-max 정규화입니다. 학습과 서빙의 기준이 다르면 같은 값이 다른 숫자로 들어갑니다.

scaler.json은 학습 구간에서 한 번만 만들고, 모델과 한 번들로 묶어 계속 씁니다.

※7
계절성과 같은 달 기준

매년 반복되는 정상적인 변화입니다. 전월과 비교하면 여름 같은 계절 변화를 드리프트로 착각합니다.

외기·습도·냉각수 PSI는 같은 달 기준이면 0.28~0.46, 1년 전체를 하나로 묶은 기준이면 4.7~5.6입니다.

4요청 하나의 여정

식각 장비※8의 최근 20사이클※9로 30분 뒤 이상 점수※10를 묻는 /predict 호출 하나를 따라갑니다. 모델 앞에는 입력 검증※11과 전처리가 있고, 전처리는 학습 때와 같은 transform()과 같은 scaler.json을 씁니다.

개념 짚기
※8
식각(Etch)과 FDC

식각은 플라즈마로 웨이퍼 위의 막을 패턴대로 깎는 공정입니다. FDC는 센서마다 고정된 상·하한을 두고 경보를 내는 기존 감시 방식입니다.

센서 하나씩이 아니라 12종을 20사이클 동안 함께 보고 점수 하나로 요약합니다.

※9
사이클과 SEQ_LEN

사이클은 장비의 공정 한 번(30분), SEQ_LEN은 모델이 한 번에 보는 과거 사이클 수입니다.

SEQ_LEN은 20(10시간)이고 입력 모양은 (20, 12)입니다.

※10
이상 점수와 위험 등급

장비 상태를 0~100으로 나타낸 값입니다. 70 이상은 HIGH, 40~70은 WARNING, 40 미만은 NORMAL입니다.

현재가 아니라 30분 뒤 공정의 점수를 예측합니다.

※11
입력 스키마와 422

요청 형식을 Pydantic으로 정의해 두고, 맞지 않으면 모델을 부르기 전에 422로 돌려보냅니다.

정확히 20개, 30분 간격의 시간순, 압력·RF 양수, 정의되지 않은 필드 금지.

※12
엔드포인트와 상태 코드

엔드포인트는 기능별 주소이고, 상태 코드는 처리 결과입니다. 200 성공, 4xx 요청 문제, 5xx 서버 문제입니다.

400 형식 오류, 404 없는 장비·파일, 413 64MiB 초과, 422 입력 검증 실패, 503 모델 미준비.

5Lazy와 Eager: 로딩 시간을 누가 기다리나

모델을 메모리에 올리는 데 약 2.5초가 걸립니다. Lazy에서는 첫 사용자가, Eager에서는 서버 기동이 그 시간을 떠안습니다※13. 아래 막대는 실제 측정값을 같은 시간 축에 그린 것입니다.

개념 짚기
※13
Lazy / Eager 로딩

모델을 첫 요청 때 메모리에 올리면 Lazy, 서버가 뜰 때 올리면 Eager입니다. 로딩 시간을 누가 기다리느냐가 달라집니다.

Lazy의 첫 요청은 2.60초, Eager의 첫 요청은 0.031초입니다. Docker는 Eager로 띄웁니다.

※14
/health와 /ready

/health는 프로세스가 살아 있는지, /ready는 모델을 들고 요청을 받을 준비가 됐는지를 확인합니다.

Docker 헬스체크는 /ready를 봅니다. 모델이 없으면 503입니다.

6버전과 배포 게이트

학습할 때마다 MLflow에 새 버전이 기록되지만※15, 서빙이 읽는 것은 @Production 별칭※16이 가리키는 한 버전뿐입니다. 게이트※17를 통과한 버전만 별칭을 가져갈 수 있고, 게이트는 RMSE※18와 HIGH 등급의 Precision·Recall※19로 판단합니다.

개념 짚기
※15
실험 추적(MLflow Tracking)

학습할 때마다 설정(params), 성능(metrics), 결과물(artifact)을 남겨서 어떤 모델이 어떻게 만들어졌는지 추적하는 일입니다.

데이터 해시, epoch, 검증·테스트·드리프트 지표를 실험 EtchGuard-AIOps에 남깁니다.

※16
레지스트리·버전·alias

레지스트리는 등록된 모델의 버전 목록이고, alias는 특정 버전을 가리키는 이름표입니다.

서빙은 models:/Semiconductor_Etch_LSTM@Production만 읽으므로 버전이 늘어도 서빙 코드는 바뀌지 않습니다.

※17
배포 게이트

정해 둔 품질 기준을 넘은 모델만 운영에 올리는 관문입니다. 통과하지 못한 모델도 기록은 남습니다.

검증 RMSE 4.0 이하, HIGH Recall 0.80 이상, Precision 0.80 이상.

※18
RMSE

예측과 실제의 차이를 제곱해 평균을 낸 뒤 제곱근을 씌운 값입니다. 큰 오차에 더 민감하고 단위가 점수와 같습니다.

√mean((실제−예측)²). 정상 테스트 3.08점, 드리프트 구간 8.07점.

※19
Precision과 Recall

Precision은 HIGH 경보 가운데 실제로 HIGH였던 비율이고, Recall은 실제 HIGH 가운데 경보로 잡아낸 비율입니다.

Recall이 낮으면 불량 웨이퍼가 진행되고, Precision이 낮으면 멀쩡한 장비를 세웁니다.

7드리프트 판정: 한 번 튄 것과 계속 나쁜 것

확정 점수가 들어오면 장비별로 (예측, 실제) 쌍을 24개(12시간)씩 묶어 RMSE를 계산합니다. 5.0을 넘는 윈도우※20가 3번 연속 나오면 드리프트※21로 판정합니다. 1회가 아니라 3회 연속으로 정한 이유는 오탐과 미탐※22의 균형 때문입니다. 판정은 예측 오차로 하고※23, 입력 분포(PSI※24)는 원인 센서를 짚는 데만 씁니다. 아래는 최종 실행의 실제 윈도우 값입니다.

원인 센서는 어떻게 고르나. 배치 입력을 2023–24년 같은 달의 분포와 비교해 센서별 PSI를 구하고, 학습 기간의 평소 PSI로 나눈 배율 상위 3개를 경보에 붙입니다. 드리프트 주간 ETCH-01은 rf_power_w ×10.2, vibration_mm_s ×2.6, chamber_pressure_mtorr ×2.4로, 데이터에 실제로 주입된 변화(RF↓, 진동↑, 압력↑)와 일치했습니다. 이 순위는 경보를 울리는 데 쓰지 않고 점검 순서를 안내하는 데만 씁니다.
개념 짚기
※20
윈도우와 연속 판정

오차를 일정 개수씩 묶어 판단하는 단위가 윈도우입니다. 짧으면 잡음에 민감하고, 길면 반응이 느립니다.

24쌍(12시간) 윈도우가 5.0을 3번 연속 넘으면 DRIFT, 1~2번이면 WATCH입니다.

※21
데이터 드리프트와 컨셉 드리프트

입력 분포가 바뀌면 데이터 드리프트, 같은 입력에 대한 정답 관계가 바뀌면 컨셉 드리프트입니다. 둘 다 에러 없이 예측을 틀리게 만듭니다.

07-20 이후 압력↑ RF↓ 진동↑와 열화 가속이 겹쳐 RMSE가 3.08에서 8.07로 올랐습니다.

※22
오탐·미탐과 알람 피로

기준을 낮추면 미탐이 줄고 오탐이 늘며, 높이면 그 반대입니다. 오탐이 잦으면 사람들이 경보를 무시하게 됩니다.

1회 판정은 정상 운전 중에도 장비당 월 2.06회 오탐, 3회 연속은 0회입니다(대신 탐지에 36시간).

※23
성능 감시와 입력 감시

정답이 있으면 예측 오차로 직접 판정하고, 정답이 늦게 오면 입력 분포 변화로 먼저 짐작합니다.

판정은 예측 오차(RMSE)로 하고, 입력 분포(PSI)는 원인 센서를 짚는 데만 씁니다.

※24
PSI

기준 분포와 현재 분포를 구간별 비율로 비교한 값입니다. Σ(현재−기준)×ln(현재÷기준)이며, 보통 0.25를 넘으면 크게 변했다고 봅니다.

장비 열화 때문에 정상일 때도 1을 넘기 쉬워서, 평소 PSI 대비 배율(예: ×10.2)로 원인 센서 순위만 매깁니다.

8재학습 시퀀스: 3초 동안 일어나는 일

드리프트 배치를 보낸 요청은 재학습을 기다리지 않고 곧바로 200을 받습니다. 재학습은 백그라운드 스레드※25에서 돌고, 통과하면 서빙 모델을 멈추지 않고 교체합니다※26. 시각은 최종 실행의 aiops.log 기준입니다.

재학습 데이터는 어디서 오나. 드리프트를 감지한 배치의 마지막 시각(2025-07-27 13:30)을 기준으로, 데이터 저장소(최신 업로드 CSV)에서 직전 7일 치를 장비 5대 모두 가져옵니다. 장비별로 시간 순서를 지켜 앞 80%(1,340건)로 학습하고 뒤 20%(340건)로 검증합니다. 스케일러는 base 번들의 것을 그대로 복사합니다.
개념 짚기
※25
백그라운드 작업과 락

오래 걸리는 작업을 요청 처리와 분리해서 돌리고, 같은 작업이 동시에 두 번 실행되지 않도록 막는 장치입니다.

batch-test는 곧바로 200을 받고, 재학습 중에 들어온 다른 장비 요청은 retrain_in_progress를 받습니다.

※26
무중단 교체

서비스를 멈추지 않고 모델을 바꾸는 일입니다. 캐시를 비우기만 하면 다음 요청이 로딩을 기다리고, 비우지 않으면 옛 모델이 계속 응답합니다.

reload()가 새 모델을 먼저 올려 둔 뒤 참조만 바꿉니다.

9게이트 재검증: 무엇을 넘어야 교체되나

재학습 후보는 세 조건을 모두 만족해야 합니다. 최근 홀드아웃에서 기본 게이트를 넘어야 하고, 현 Production보다 나아야 하며※27, 드리프트에 맞추다가 정상 상태를 잊지 않았는지※28 고정 정상셋으로 확인합니다. 하나라도 못 넘으면 기존 버전이 그대로 서비스됩니다※29.

개념 짚기
※27
Champion / Challenger · 회귀 테스트

서비스 중인 모델과 후보 모델을 같은 데이터로 비교하고, 예전에 잘하던 것을 여전히 잘하는지 고정 데이터로 다시 확인하는 절차입니다.

홀드아웃 RMSE 7.86 → 2.64, 고정 정상셋 2,410건 RMSE 3.39(기준 4.0 이하).

※28
Fine-tuning · warm start · 망각

이미 학습된 가중치에서 이어서 조금 더 학습하는 방식입니다. 적은 데이터로 처음부터 학습하면 결과가 불안정하고 예전 패턴을 잊어버립니다(망각).

최근 7일 데이터로 학습률 1e-4, 10 epoch. 처음부터 학습하면 정상셋 RMSE가 6.43까지 나빠집니다.

※29
롤백

문제가 생겼을 때 이전 버전으로 되돌리는 일입니다. 게이트에서 떨어지면 기존 버전을 그대로 두는 것이 자동 롤백 역할을 합니다.

수동 롤백은 registry rollback --version N이며, 게이트 통과 이력이 있는 버전만 허용합니다.

모델 품질과 별개로 서비스 자체도 지켜봅니다. 모든 요청은 미들웨어를 거치며 엔드포인트별로 응답 시간과 결과 코드가 집계되고, /monitoring/status에서 확인할 수 있습니다※30※31.

※30
p50 · p95 지연시간

요청 응답 시간을 줄 세웠을 때 50%, 95% 지점의 값입니다. 평균은 몇 건의 느린 요청을 가려 버리므로 p95로 체감 품질을 봅니다.

최근 1,000건 기준. 7일 배치 판정 p50 35ms, p95 105ms.

※31
처리량과 에러율

처리량은 일정 시간 동안 처리한 요청 수, 에러율은 그중 실패한 비율입니다. 4xx는 요청 쪽, 5xx는 서버 쪽 문제라 따로 셉니다.

엔드포인트별 요청 수와 4xx·5xx 건수를 집계하고, 최종 실행의 5xx는 0건이었습니다.

11Docker: 빌드할 때와 실행할 때

이미지※32를 만들 때 학습, 등록, 승격까지 끝내 두므로 컨테이너는 뜨자마자 Production 모델을 들고 시작합니다. 호스트의 MLflow DB를 복사하지 않아 절대경로 문제가 없고, 의존성을 소스보다 먼저 설치해 레이어 캐시※33를 활용합니다.

개념 짚기
※32
이미지와 컨테이너

이미지는 코드·라이브러리·모델을 묶은 실행 꾸러미이고, 컨테이너는 그 이미지를 실제로 띄운 실행 단위입니다. 어디서 실행해도 환경이 같습니다.

빌드할 때 학습과 등록을 끝내 두고, 실행하면 Eager로 바로 서빙합니다.

※33
레이어 캐시

Dockerfile의 각 줄이 층으로 저장되고, 바뀌지 않은 층은 다시 실행하지 않는 기능입니다.

의존성을 먼저 설치하므로 코드만 고치면 TensorFlow를 다시 설치하지 않습니다.
